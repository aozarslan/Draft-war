# S8.5 — ROUND COMBAT: design and audit

No production code was written for this document, and no migration exists yet.
What ran: the existing suite, the live schema, and a simulation driving the
**real** `simulateBattle` engine and the **real** `pairRound` function against
the real catalogue.

---

## 1. EXECUTIVE SUMMARY

S8.5 turns `round_matchups.battle_result` from null into an authoritative
result. The engine that does the fighting already exists, is pure, is seeded and
is already replayed frame-aligned across phones. Almost none of this milestone
is combat; it is **plumbing, idempotency and one recalibration.**

Three findings decide the design, and two of them contradict work already
approved.

**Finding 1 — the damage curve in `docs/S8-DESIGN.md` is calibrated against an
assumption the real engine does not satisfy.** That curve is
`(8 + 2.4 × survivors) × (1 + 0.18 × (round−1))`, capped at 32, and it was fitted
when `survivors` was a uniform draw in a toy model. Measured over 4,000 real
5v5s, the winner keeps a mean of **3.07** fighters and the loser is **always
wiped to 0%** — the engine fights to elimination. Substituting the real
distribution, every loss from about round five onward costs the cap. Simulated
end to end, that leaves a four- or five-player table on a **median of 1–5 HP**
with 1.9–2.4 eliminations per match. §16 replaces the curve.

**Finding 2 — the encounter penalty S8.3 measured has inverted, and the knob is
violently sensitive.** With a median-strength opponent and full loss damage, an
encounter round costs **−1.20 HP (3P) / +0.17 HP (5P)** relative to a duel round:
neutral, which is the target. But an 8% error in the opponent's strength moves
the encounter win rate from **87% to 6%**. The construction of that board is
therefore load-bearing and gets its own tests.

**Finding 3 — `simulateBattle` requires a map and an event card, and a match
round has neither.** The legacy flow gets them from a map vote and an event
draw; a match has no such phases (events are S8.8). §3 derives one battlefield
per round from the match seed.

Everything else reuses what exists: the replay projection, the renderer, the
clock, the atomic-store pattern, and the phase guards. No new replay system, no
new table, and `RULES_VERSION` does not move.

## 2. CURRENT ARCHITECTURE

### 2.1 The engine

`simulateBattle(input) → BattleResult` — pure, deterministic in `seed`, already
N-team. It consumes:

```ts
{ teams, map, event, charactersById, seed, categoryIds?, bands? }
```

and produces `seed`, `rulesVersion`, `mapId`, `eventId`, `categoryIds`, `log[]`
(each entry time-stamped with `atMs` and carrying `hpAfter`), `durationMs`,
`teams[]` (rank, points, survivors, `remainingHpPct`, `winProbability`,
`teamRating`, synergies), `combatants[]`, `winnerPlayerId`, `upset`,
`turningPoint`, `mvp`, `awards`.

The round loop, damage maths, RNG draw order, synergy cap and crossover
normalisation are all out of scope for S8.5 and must not move.

### 2.2 What a match already has

| Table | Holds | S8.5 uses it |
| --- | --- | --- |
| `matches` | seed, round_no, phase, phase_started_at, round_count | seed and round for RNG namespaces |
| `match_players` | hp, credits, streak, round_wins, eliminated_at | HP written; credits untouched |
| `board_slots` | who owns what, zone, slot | the fighting board |
| `match_acquisitions` | the price paid, per character | `price` on each combatant |
| `round_matchups` | player_a, player_b, kind, rating_a/b, reason, **battle_result**, started_at, settled_at, winner_player_id, damage | everything S8.5 writes |
| `games` (match rounds) | the round's draft | not read by combat |

### 2.3 The live definitions S8.5 must extend

Checked with the `liveDefinitionOf` helper S8.3 added, not by memory:

```
dw_advance_match_phase(5 args)  0030 → 0031 → 0032   LIVE = 0032
dw_match_tick(1 arg)            0030 → 0031 → 0032   LIVE = 0032
dw_match_snapshot(1 arg)        0030 → 0031 → 0032   LIVE = 0032
dw_resolve_auction(1 arg)       0001 → 0005 → 0031   LIVE = 0031
dw_store_battle(2 args)         0001                 LIVE = 0001  (legacy only)
```

Any S8.5 test that asserts something about the first three **must** read them
through `liveDefinitionOf`. Reading 0030 or 0031 would check a definition the
database never executes — the trap that has already disconnected two tripwires
in this project.

### 2.4 The replay path, and why it does not need rebuilding

```
result (jsonb) ─► toReplay(result, context) ─► sceneAt(replay, elapsed) ─► BattleRenderer
```

`buildStage` takes `ProjectableResult`, declared **structurally** so a live room
and a shared public match already go through the same builder. A round matchup
is a third caller of the same shape. The only new thing needed is where the
clock comes from: `BattleStage` currently reads `snapshot.game.battleStartedAt`,
and a matchup's clock is `round_matchups.started_at`.

`sceneAt` seats by `seat === 0 ? 0 : 1`. A duel is 1v1, which is exactly the
shape the arena was built for.

## 3. BATTLE INPUT MODEL

Every input is server state read inside one transaction. Nothing comes from a
request body.

| Input | Source | Notes |
| --- | --- | --- |
| player A | `round_matchups.player_a` | fixed at pairing time |
| player B | `round_matchups.player_b` | null ⇒ encounter |
| A's board | `board_slots WHERE match_id, player_id AND zone <> 'BENCH'`, ordered by `slot`, capped at 5 | the bench does not fight |
| B's board | same | |
| price per fighter | `match_acquisitions.final_price` | feeds `valueScore` only |
| formation | `players.formation` | already per-player |
| categories | `matches.category_ids` | drives crossover normalisation |
| bands | `computeAxisBands(all characters)` | full pool, not the drafted few |
| map + event | **derived from the seed** — see below | a match has no vote and no draw |
| seed | `battle:${match.seed}:${round}:${pairingIndex}` | §7 |

**Character HP is not an input.** `simulateBattle` computes each fighter's
`maxHp` from its axes and starts every fight at full. Player HP
(`match_players.hp`) is a *match* resource, consumed by §11's damage rule after
the battle; it never enters the battle.

**Positioning does not affect combat in S8.5.** S8-DESIGN puts that in S8.7 with
a ±10% cap and a `RULES_VERSION` bump. Board *contents* are read; `zone` is read
only to exclude the bench.

**The board is frozen when the pairing is written.** The auction closed two
phases earlier and nothing between `BOARD_UPDATE` and `COMBAT` can add a
character, so reading `board_slots` at resolution time yields the same board
that existed at pairing time. This is a property of the phase order rather than
a lock, and §19 mutates the phase order to prove the tests notice.

**The battlefield.** One map and one event card per round, drawn from
`createRng("env:" + matchSeed + ":" + round)` over the existing `MAPS` and
`EVENT_CARDS`. Every matchup in a round shares them, which is both thematically
right — it is one round on one battlefield — and fair, since neither side chose
it. Simulated with and without: upset rate 7.7% vs 7.9%, encounter cost within
noise. It costs nothing and uses content that already exists.

## 4. DUEL RESOLUTION

```
teams = [
  { playerId: A, nickname: A.nickname, characters: boardOf(A), formation: A.formation },
  { playerId: B, nickname: B.nickname, characters: boardOf(B), formation: B.formation },
]
seed = `battle:${match.seed}:${round}:${pairingIndex}`
```

`simulateBattle` returns a winner. Then:

```
winner   = result.winnerPlayerId
loser    = the other seat
damage   = damageFor(round, winnerTeam.remainingHpPct)      -- §11
loser.hp = clampHp(loser.hp - damage, round)                 -- existing helper
winner.round_wins += 1 ; winner.streak += 1 ; loser.streak = 0
```

Both seats are always in the same match and both are alive — the pairing
function excludes eliminated seats and `dw_pair_round` re-checks it.

## 5. ENCOUNTER RESOLUTION

**There is no free round.** The odd seat fights a board the server builds.

```
opponentSeed  = `encounter:${match.seed}:${round}:${pairingIndex}`
targetPower   = median average board power across live seats this round
size          = the odd seat's own board size (never more than 5)
board         = the `size` characters from the match's categories whose
                gamePower is closest to targetPower, shuffled by opponentSeed,
                excluding everything in `match_acquisitions`
```

Excluding acquired characters matters: the arena must not field a character
somebody at the table owns.

The synthetic side takes a **reserved pseudo-id** (`"encounter"`) inside the
`BattleResult` only. It is never written to `round_matchups.player_b`, which is
a foreign key to `players` and stays NULL. `winner_player_id` stays NULL when the
arena wins. `toReplay`'s context supplies the nickname.

**Full damage on a loss, nothing on a win** beyond the ordinary round reward.
No HP recovery, no bonus acquisition, no board advantage.

### The calibration, measured

Cost of a round, per player-round, mean HP lost:

| Opponent power | 3P encounter | 3P duel | delta | 5P encounter | 5P duel | delta | win rate |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.86 × median | 0.40 | 8.09 | **−7.69** | 0.59 | 7.89 | −7.30 | 94–96% |
| 0.92 × median | 1.04 | 8.07 | −7.03 | 1.48 | 7.89 | −6.41 | 87–91% |
| **1.00 × median** | **6.81** | **8.01** | **−1.20** | **8.03** | **7.86** | **+0.17** | **46–52%** |
| 1.08 × median | 16.85 | 7.97 | +8.88 | 17.42 | 7.83 | +9.59 | 6% |

**1.00 is the answer**, and the table is the reason it needs tests: an 8% error
in either direction turns a neutral round into a near-free win or a near-certain
beating. The engine's win probability is very steep near parity.

## 6. SERVER AUTHORITY

There is **no new client action**. Combat is not something a player does; it is
something the round does to them.

| A client could send | What happens |
| --- | --- |
| `winner`, `damage`, `hpAfter`, `eliminated`, `reward`, `seed`, `timeline` | no code path reads them; there is no field to read them into |
| a matchup id | not accepted — resolution takes a room and finds the round's own matchups |
| a resolve request for somebody else's matchup | there is no per-matchup endpoint |
| `ADVANCE_MATCH` | already argument-free and host-gated (S8.1), and §12's guard refuses to leave `COMBAT` early |

The clients that drive combat forward are the same ones that drive every other
phase: any of them may call the tick, and the tick is idempotent.

## 7. DETERMINISTIC RNG

Existing namespaces, verified by reading the code:

```
category:${roomId}:${stateVersion}      category draw
maps:${gameSeed}                        map candidates
lock:${gameSeed}                        map tie-break + event draw
battle:${seed}                          simulateBattle, internally
${matchSeed}:${round}                   round draft queue          (S8.2)
matchmaking:${matchSeed}:${round}       pairing permutation        (S8.3)
```

S8.5 adds three, none of which collides:

```
env:${matchSeed}:${round}                      the round's map and event
battle:${matchSeed}:${round}:${pairingIndex}   the fight
encounter:${matchSeed}:${round}:${pairingIndex} the arena's board
```

`simulateBattle` internally prefixes with `battle:` again, giving
`battle:battle:…`. That is harmless but ugly; the seed passed in should be
`${matchSeed}:${round}:${pairingIndex}` and the engine's own prefix left to do
its job. **Decision: pass the unprefixed triple.**

Forbidden and asserted against in source: `Math.random`, `Date.now`,
`new Date`, request order, client payload, row order. `started_at` is written
*by* the resolution and never read *into* it.

## 8. BATTLE RESULT AND REPLAY MODEL

`round_matchups.battle_result` stores the whole `BattleResult` verbatim, exactly
as `games.battle_result` does for a legacy game. It is immutable once written.

**What must be recorded as evidence, because it cannot be reconstructed:**

| Field | Why it cannot be rebuilt later |
| --- | --- |
| the whole `log[]` | the fight is a function of a seed *and the boards at that moment*; boards grow every round |
| `teams[].winProbability`, `teamRating` | same |
| `mvp`, `upset`, `turningPoint`, `awards` | derived from the log, which is derived from state that has moved on |
| `mapId`, `eventId` | derivable from the seed today, but only while the map and event tables never change |
| `rulesVersion` | the whole point of a rules version |
| `damage` (the match-level HP cost) | derived from `remainingHpPct` **and the round number**; both are in the row, so this is a convenience column rather than evidence |

**What is not stored, because it is already true elsewhere:** the boards (in
`board_slots` + `match_acquisitions`), the pairing reason and ratings (already on
the row from S8.3, and immutable — §13), the seed (derivable from `matches.seed`
plus the row's own `round_no` and `pairing_index`).

**Replay** reuses `buildStage` unchanged. The one addition is a second source
for the clock: `round_matchups.started_at` instead of `games.battle_started_at`.
No parallel replay system, no second projection.

## 9. ATOMICITY AND TRANSACTIONS

The battle is computed in **TypeScript** (the engine lives there, is pure, and is
tested there), then persisted by **one plpgsql function in one transaction**.
This is the split S8.2 and S8.3 both use, for the same reason.

`dw_resolve_matchup(p_room_id, p_pairing_index, p_result jsonb)` does, under
`SELECT … FOR UPDATE` on the match row:

1. verify the match is ACTIVE and at `COMBAT` (or `FINAL_COMBAT`);
2. read the matchup row for `(match, round_no, pairing_index)`;
3. **if `battle_result IS NOT NULL`, return `{ok, noop, alreadyResolved}` and
   change nothing**;
4. write `battle_result`, `started_at = now()`, `settled_at = now()`,
   `winner_player_id`, `damage`;
5. apply HP to the loser with the round's clamp;
6. bump `round_wins` / `streak`;
7. set `eliminated_at` when HP reaches zero and the round allows it;
8. bump `state_version`.

Steps 3–7 are one statement sequence in one transaction. **Partial state is not
reachable**: either the result, the HP, the streaks and the elimination all
land, or none of them do. This is the same shape as `dw_store_battle`, which has
been in production since 0001, and the same shape as `dw_resolve_auction`, where
the debit and the acquisition record are written under one lock precisely so they
cannot disagree.

Answering the question as posed: **a database function, not a server
transaction.** The Node layer cannot hold a transaction across several RPCs, and
the failure mode being prevented — HP applied without a result, or a result
without HP — is exactly what a single function prevents by construction.

## 10. CONCURRENCY AND IDEMPOTENCY

**The invariant: one matchup, one authoritative resolution.**

Enforced by the `battle_result IS NOT NULL` check under the match row lock. A
second caller reads a committed result and returns `noop`. It does not apply
damage, does not eliminate, does not pay, does not overwrite.

That check is *cheap but not sufficient on its own*: two callers could both read
null before either writes. The match row lock is what serialises them — the same
mechanism that made S8.2's phase advance safe.

**Different matchups in the same round must not block each other unnecessarily.**
They do share the match row lock, so they serialise. At three matchups per round
that is three short transactions, which is acceptable and much simpler than a
per-matchup lock — and it removes any question about two matchups racing to
eliminate the same player. **Decision: one lock, accept the serialisation.**

Planned tests: 2, 6 and 10 concurrent resolutions of the same matchup, expecting
exactly one authoritative result and the rest `noop`; and a check that a round's
three matchups all resolve when driven concurrently.

## 11. HP, DAMAGE AND ELIMINATION

### The recalibrated curve

```
damage = clamp( round( (6 + 14 × winnerRemainingHpFraction)
                       × (1 + 0.12 × (round − 1)) ), 4, 24 )
```

`winnerRemainingHpFraction` is `teams[winner].remainingHpPct / 100` — the
engine's own number, copied, not recomputed. A winner who barely survived costs
their opponent less than one who walked through them, which is the "remaining
enemy power" the original brief asked for and a better-distributed signal than a
survivor count that clusters at 3.

Measured against the real engine, 250 matches per configuration:

| Curve | 3P median HP | 3P elim | 4P median HP | 4P elim | 5P median HP | 5P elim |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **A** — S8-DESIGN as written | 6 | 1.41 | 3 | 1.93 | 4 | 2.35 |
| B — softer survivors | 59 | 0.17 | 55 | 0.22 | 55 | 0.16 |
| **C — chosen (winner HP)** | **38** | **0.64** | **38** | **0.98** | **38** | **1.17** |
| D — winner HP, soft | 53 | 0.35 | 52 | 0.49 | 51 | 0.49 |
| E — mixed | 49 | 0.43 | 49 | 0.60 | 49 | 0.65 |

Curve A wipes the table. Curve B makes HP decorative. **C leaves a match ending
on a median of 38 HP with about one elimination — tense, survivable, and the
last round still matters.**

### Elimination

* `clampHp(hp, round)` already exists and floors at 1 before round 6, 0 from
  round 6. Reused, not reimplemented.
* HP can never go below zero, and never below 1 before round 6.
* **A player can be eliminated at most once**: `eliminated_at` is set only when
  it is currently null, inside the same locked transaction. A second matchup
  cannot re-eliminate them, and the pairing function has already excluded them
  from later rounds.
* One matchup's resolution touches only its own two seats' HP. Asserted by a
  test that resolves one matchup and checks every other seat's HP is byte-equal.

### The upset modifier

S8-DESIGN specifies `×1.15` when the loser was the forecast favourite. The
engine flags `upset` on **7–8%** of duels, so this now applies to a much smaller
base than the original design assumed. **Decision: keep it**, because it is
cheap, it is legible ("you were favoured and lost"), and at 8% frequency it
cannot distort the curve. It is applied before the clamp.

## 12. ROUND COMPLETION

`COMBAT` is complete when **every** matchup of the current round has a non-null
`battle_result`.

```sql
-- inside dw_advance_match_phase, for m.phase in ('COMBAT','FINAL_COMBAT')
if exists (select 1 from round_matchups
            where match_id = m.id and round_no = m.round_no
              and battle_result is null)
then return dw_err('COMBAT_INCOMPLETE', 'Not every fight has finished.');
end if;
```

* The **timer cannot bypass it.** `COMBAT` has no deadline of its own (S8.1 left
  it null deliberately), and the guard runs on both the clock path and the host
  path.
* The **host cannot bypass it.** The guard is inside the function, after the
  host check, not in the UI.
* A round with no matchups at all — fewer than two live players — is handled by
  the existing `v_live >= 2` shape S8.3 used for `NOT_PAIRED`.

`dw_match_tick` gains a `NEEDS_COMBAT` report when the phase is `COMBAT` and some
matchup is unresolved, mirroring `NEEDS_ROUND_AUCTION` and `NEEDS_ROUND_PAIRING`.

## 13. MATCHMAKING INTEGRATION

`rating_a`, `rating_b` and `reason` are the **immutable snapshot of a pairing
decision** and S8.5 must never write them. A test asserts that resolving a
matchup leaves all three byte-equal.

Combat *feeds* future pairings only through state the pairing function already
reads: HP (`match_players.hp`) and, when S8.5 lands, `round_wins` — which is what
`recentForm` will be derived from in a later milestone. `MATCHMAKING_WEIGHTS.form`
stays **0** in S8.5; turning it on is a separate, testable change, and a test
already holds it at zero.

## 14. FINAL COMBAT

**Same engine, same input model, same replay format, same determinism, same
persistence.** The differences are three, and all of them are bookkeeping:

| | Round combat | Final combat |
| --- | --- | --- |
| Pairing source | `pairRound` | the championship bracket (S8.9) |
| `kind` | `DUEL` / `ENCOUNTER` | `PLAY_IN` / `SEMIFINAL` / `FINAL` — all already in the check constraint |
| Loser's fate | HP damage, elimination from round 6 | knocked out of the bracket |
| Round number in the seed | `round` | `round` (= `round_count`), plus `pairing_index` which the bracket assigns |

**Decision: `dw_resolve_matchup` handles both**, gated on the phase being
`COMBAT` **or** `FINAL_COMBAT`. Writing a second resolver for the final would be
a second place where damage and elimination are applied — which is precisely the
kind of duplication this project has removed twice already.

S8.5 builds the resolver so that `FINAL_COMBAT` works the moment S8.9 writes
bracket rows. It does **not** build the bracket.

## 15. STATE MACHINE

```
POSITIONING ──advance──► COMBAT ──all matchups resolved──► ROUND_END
                            │                                  │
                            └── unresolved ⇒ COMBAT_INCOMPLETE  │
                                                                ├─ round < total ─► ROUND_START (round+1)
                                                                └─ round = total ─► CHAMPIONSHIP
CHAMPIONSHIP ──advance──► FINAL_COMBAT ──all resolved──► MATCH_RESULTS
```

Behaviour per transition:

| Transition | Normal | Missing battle | Duplicate request | Concurrent | Bad client input | Refresh | Timer |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `POSITIONING → COMBAT` | advances, then resolves every matchup | n/a | `noop` (`p_from` stale) or `CONCURRENT_PHASE_ADVANCE` | one winner, rest rejected | extra fields ignored | reads state | 30s deadline |
| resolve a matchup | writes result + HP once | n/a | `noop, alreadyResolved` | match row lock ⇒ one winner | no endpoint accepts a result | reads stored result | tick retries |
| `COMBAT → ROUND_END` | advances | **`COMBAT_INCOMPLETE`** | `noop` | one winner | ignored | reads state | **cannot bypass** |
| `ROUND_END → ROUND_START` | round += 1 | n/a | `noop` | one winner | ignored | reads state | 5s deadline |
| `CHAMPIONSHIP → FINAL_COMBAT` | advances | n/a | `noop` | one winner | ignored | reads state | 10s deadline |
| `FINAL_COMBAT → MATCH_RESULTS` | advances, match FINISHED | `COMBAT_INCOMPLETE` | `noop` | one winner | ignored | reads state | cannot bypass |

`COMBAT` gains a deadline for the first time: it must last at least as long as
the longest `durationMs` among the round's results, so a viewer sees the fight.
**Decision: the deadline is set when the last matchup of the round resolves**, to
`now() + max(durationMs) + a small tail`, computed in TypeScript where the
phase-deadline table already lives.

## 16. ANTI-EXPLOIT

| Attempt | Outcome |
| --- | --- |
| forged `winner` / `damage` / `hpAfter` / `eliminated` / `reward` / `seed` / `timeline` in any request body | no route reads them; no action type declares them |
| resolve another player's matchup | there is no per-matchup endpoint; resolution takes a room and iterates the round's own rows |
| resolve another round's matchup | the function selects by `round_no = m.round_no` from the locked match row |
| re-resolve a settled matchup | `battle_result IS NOT NULL` ⇒ `noop` |
| force a favourable battlefield | the map and event come from `env:${matchSeed}:${round}`; nothing a player controls is in that string |
| bench a fighter after seeing the matchup | positioning closes before `MATCHMAKING`; the phase order is the guard, and §19 mutates it |
| disconnect to avoid a fight | resolution reads persisted state; connection status is not an input |
| stall so the timer skips the fight | `COMBAT_INCOMPLETE` blocks both the clock and the host |
| lose on purpose to draw a weaker opponent | HP carries weight 0.10 in the pairing rating (S8.3); throwing a round trades real HP for a rating shift an order of magnitude below the history terms |

## 17. SIMULATION RESULTS

Real `simulateBattle`, real `pairRound`, real catalogue (Marvel + DC crossover),
mandatory acquisition R1–R5 and 60% take-up R6–R8.

### What a real 5v5 leaves behind — 4,000 battles

```
winner survivors:  0:0%  1:10%  2:22%  3:31%  4:28%  5:10%     mean 3.07
winner HP%  mean:  36.9
loser  HP%  mean:   0.0     (the engine fights to elimination)
```

This is the measurement that invalidates the S8-DESIGN curve.

### End to end, with the chosen curve — 250 matches per size

| | avg dmg | median dmg | elim/match | encounter win% | median end HP | upset% | comeback% | runaway% |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2P | 15.3 | 15 | 0.26 | — | 61 | 8.5 | — | 69.6 |
| 3P | 15.5 | 15 | 0.64 | 51.2 | 38 | 7.4 | 23.2 | 51.6 |
| 4P | 16.0 | 16 | 0.98 | 51.3 | 38 | 7.3 | 5.6 | 42.4 |
| 5P | 15.6 | 15 | 1.17 | 45.2 | 38 | 7.9 | 1.6 | 28.0 |

### Encounter calibration

See §5. Neutral at 1.00 × median board power; the knob is steep on both sides.

### Metrics that had to be repaired, again

The "encounter advantage" metric inherited from S8.3 — *does the seat with the
most encounters win the match more often than chance* — reported **−12.4 even
when the encounter was being won 95.9% of the time.** It is measuring the
structure of the bye rotation, not an advantage: S8.3's own scheduler spreads
byes to within one, so "the seat with the most" is a near-tie broken arbitrarily.

Replaced with a direct per-player-round comparison: **mean HP lost in a round
that was an encounter, against mean HP lost in a round that was a duel.** That
number tracks the calibration knob monotonically and sensibly, which the old one
did not.

This is the third bye/encounter metric in this project to mislead. The lesson
worth keeping: *a metric aggregated to the match level cannot measure the value
of a single round.*

### Still unresolved by S8.5

**Comeback at four and five players is 1.6–5.6%.** Softer curves raise it only to
8%. Matchmaking does not move it (S8.3 measured that). This is what the event
system, bounties and the underdog reward exist for, and it is S8.8's problem —
recorded here so it is not discovered as a surprise then.

## 18. SCHEMA IMPACT

**`round_matchups` is sufficient as it stands.** Every field S8.5 writes already
exists: `battle_result`, `started_at`, `settled_at`, `winner_player_id`,
`damage`.

Deliberately not added:

* a matchup seed — derivable from `matches.seed` + `round_no` + `pairing_index`;
* a copy of either board — `board_slots` and `match_acquisitions` hold it, and
  the result's `combatants[]` names every fighter that took part;
* a per-matchup status column — `battle_result IS NULL` *is* the status, and a
  second encoding is a second thing that can disagree;
* an `encounter_board` column — the arena's board is in `battle_result.combatants`
  under the reserved player id, and is reproducible from the seed.

**One column is worth arguing for and is rejected:** an `encounter` flag. `kind`
already says it and `player_b IS NULL` already says it. A third encoding would
repeat S8.3's `bye_player` mistake.

So the migration is **functions only**: `dw_resolve_matchup`, plus replacements
of `dw_advance_match_phase` (the `COMBAT_INCOMPLETE` guard) and `dw_match_tick`
(the `NEEDS_COMBAT` report) and `dw_match_snapshot` (expose `battleResult` and
`startedAt` per matchup). No new table, no new column.

## 19. TEST STRATEGY

Three layers, because source-string assertions alone have now failed this
project twice.

**Layer 1 — pure functions, executed.**
`damageFor(round, winnerHpFraction, upset)`; `encounterBoardFor(seed, target,
size, excluded)`; `buildDuelInput(...)` / `buildEncounterInput(...)`;
`combatComplete(matchups, round)`. All pure, all directly invoked. The pattern
S8.3b established when three engine guards escaped a source scan.

* the same inputs give byte-identical `BattleResult`, 1,000 times;
* the encounter board is stable in its seed and never contains an acquired
  character;
* damage is clamped at both ends and never negative;
* the bench never appears in a battle input;
* board order does not depend on row order.

**Layer 2 — the migration, read live.**
Every SQL assertion goes through `liveDefinitionOf`, never a hard-coded file.
Guard conditions, not just error strings — a guard reduced to a dead branch
keeps its own message, which is how `AUCTION_INCOMPLETE` escaped in S8.3b.

**Layer 3 — the live database.**
2/6/10 concurrent resolutions of one matchup; a whole round resolved
concurrently; refresh and reconnect mid-combat; `COMBAT_INCOMPLETE` proved by
deleting a result behind the server's back, as S8.3b proved `NOT_PAIRED`;
2/3/4/5-player matches played to `MATCH_RESULTS`; legacy game untouched.

## 21. FAILURE MODES

| Failure | Behaviour |
| --- | --- |
| The engine throws mid-round | nothing was written; the tick reports `NEEDS_COMBAT` and retries. The phase cannot advance. |
| One matchup resolves, the process dies | the resolved one is committed; the others are retried. `COMBAT_INCOMPLETE` holds the phase. |
| The RPC fails after computing | nothing written — the whole write is one function call |
| A player is eliminated by matchup 0 while matchup 1 is resolving | they were never in matchup 1; the pairing gave every seat exactly one |
| The catalogue changes between pairing and resolution | `board_slots` names character ids; a missing id is dropped from the board, and a board of zero cannot fight — `dw_resolve_matchup` rejects rather than simulating an empty team |
| Two matchups both try to eliminate the same seat | impossible by pairing; also guarded by `eliminated_at IS NULL` |
| A result arrives for a round that has moved on | the function reads `round_no` from the locked match row, not from the caller |

## 22. MIGRATION PLAN

**`0033_s8_round_combat.sql`** — functions only, additive, idempotent, no drops:

* `dw_resolve_matchup(p_room_id, p_pairing_index, p_result jsonb)` — new;
* `dw_advance_match_phase` — replaced, adding `COMBAT_INCOMPLETE`, keeping every
  0032 guard;
* `dw_match_tick` — replaced, adding `NEEDS_COMBAT`;
* `dw_match_snapshot` — replaced, exposing `battleResult` and `startedAt` per
  matchup.

Deploy order tolerance is the same discipline S8.1 established: the code must not
break a room when 0033 is absent. Reads already degrade through `rpcOptional`;
`dw_resolve_matchup` is a write and must fail loudly.

## 24. CONTRADICTIONS WITH `docs/S8-DESIGN.md`

Recorded explicitly, because both were approved decisions.

**1. The damage curve is replaced.** S8-DESIGN §6.3 specifies
`(8 + 2.4 × survivingEnemyFighters) × (1 + 0.18 × (round−1))`, clamped 4–32, and
reports it as producing a median 16 HP with 1.34 eliminations at four players.
Those figures came from a toy model in which `survivors` was uniform. Against the
real engine the same curve yields a **median of 3 HP and 1.93 eliminations**.
Replaced by `(6 + 14 × winnerRemainingHpFraction) × (1 + 0.12 × (round−1))`,
clamped 4–24. The *shape* the brief asked for — remaining enemy power, a round
multiplier, an upset modifier — is preserved; only the calibration changed, and
only because it was calibrated against the wrong thing.

**2. The encounter's loss damage is confirmed at full, and the opponent's
strength is pinned.** S8-DESIGN PART 7 left "0.6× damage" and "full damage" both
on the table. Measured against the real engine, full damage at a
**median-strength** opponent is neutral (−1.2 / +0.2 HP per round). S8-DESIGN's
residual "+6.6 / +10.9 point advantage" is superseded: it came from the same toy
model and the same match-level metric that §17 shows to be unsound.

**3. S8-DESIGN's "encounter advantage" figures should not be quoted again.** The
metric behind them reports a large negative advantage for a round that is won
96% of the time. §17 documents the replacement.

## 25. GO / NO-GO CRITERIA FOR S8.5

S8.5 may be called complete only when **all** of these hold:

1. `0033` applied live and verified through `liveDefinitionOf`, not by memory.
2. One matchup, one resolution: 2/6/10 concurrent resolutions produce exactly one
   authoritative result; the rest are `noop`; no second damage, elimination or
   reward.
3. Byte-identical results for identical inputs, 1,000 repetitions.
4. No `Math.random`, `Date.now` or request-order dependency anywhere in the
   combat path.
5. `COMBAT → ROUND_END` refused while any matchup is unresolved — proved by
   deleting a result behind the server's back, on both the host and the clock
   path.
6. HP never negative; never below 1 before round 6; a seat eliminated at most
   once; one matchup's resolution provably leaves every other seat's HP
   unchanged.
7. `rating_a` / `rating_b` / `reason` byte-equal before and after resolution.
8. `players.credits` untouched by combat; `match_players.credits` unchanged by
   combat.
9. Legacy games (`match_id IS NULL`) unaffected; legacy fingerprint unchanged;
   `RULES_VERSION` still 1.
10. 2/3/4/5-player matches played to `MATCH_RESULTS` live, with every round's
    matchups resolved.
11. Refresh and reconnect mid-combat replay the stored result rather than
    recomputing it.
12. The full mutation set of §20 caught, with any escapee classified as *test
    weakness* or *equivalent mutation* and reported either way.
13. Encounter cost within ±2 HP of duel cost per player-round, re-measured after
    implementation.
14. Typecheck, full suite, and a clean production build with the dev server
    stopped.

**Nothing is implemented. No migration written, no production code changed,
nothing committed. This document is an audit, not an approval.**
